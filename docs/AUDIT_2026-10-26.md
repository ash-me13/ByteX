Status labels: PASS = ran and passed · FAIL · BLOCKED = environment could not run it · SKIPPED = deliberately not run · NOT VERIFIED.

## 1. Overall status
- Inspected: all backend code outside the three very large files, frontend services/hooks, launchers, manifests, Android sources and Gradle files, tests.

## 3. Security results
| Item | State |
|---|---|
| Backend bind | Loopback only: `main.py`, `start_bytex.py`, `start_bytex.bat` now say `127.0.0.1` explicitly (before: `main.py` used `0.0.0.0`). Static test passes. |
| `LocalOnlyGuardMiddleware` | Present, **integrated** in `main.py` (outermost, after CORS), **unit-tested** (28 tests, PASS), **not runtime-verified** (could not start FastAPI). Checks socket peer, Host header, Origin on WebSockets and non-GET methods. Ignores `X-Forwarded-For`. |
| Cross-site / DNS rebinding | Blocked by the guard in tests; not exercised against the live app. |
| `/ws/phone` and pairing from the LAN | Blocked (no exceptions). Wi-Fi pairing is off; requirements in `docs/PHONE_PAIRING_SECURITY.md`. |
| Authentication | **None.** Any local process can still call the API (including `/api/chat`, automations, memory clear). The guard is not authentication. This is the main remaining risk and needs a design decision (per-launch token between UI and backend). |
| Pairing approval | Approval endpoint no longer falls back to another pending session; expired/timed-out sessions cannot create devices (tested). Approval is still an unauthenticated loopback call. |
Do not describe ByteX as secure: the items above remain open.

## 6. Android (static review only; BLOCKED for build)
Confirmed from source: no `res/` (manifest references `@mipmap/ic_launcher[_round]`), no `gradle.properties` (`android.useAndroidX=true` needed), no Gradle wrapper, `proguard-rules.pro` missing, `MainActivity` imports `com.bytex.phone.R`. **QR scanning is a stub** (`launchQrScanner` only shows a Toast; `handleQrScanned` is never called) so pairing cannot start from the app. `PAIRING_APPROVED` falls back to a fabricated token (`"token_"+sessionId`) when the server sends none; `SecureStorageManager` silently falls back to **unencrypted** SharedPreferences if encrypted storage fails; the app uses `ws://` and the manifest does not allow cleartext (blocked on Android 9+). Protocol matches the backend: `ws://host:port/ws/phone`, `PAIRING_REQUEST` / `AUTHENTICATE`, field names `sid/sec/pc/host/port/exp`. No Kotlin was edited (cannot compile here).

## 9. Remaining risks (critical first)
1. No authentication on the loopback API; any local process can drive the agent. Decision needed (per-launch bearer token shared by launcher, UI and backend).
2. Guard integration and the single phone route registration are not runtime-verified. First thing to do on your Mac: start the app and click through (see §10).
3. Large execution paths not audited in depth (command router, coding, planner, terminal, browser/CDP).
4. Possible API-key-shaped string in a scratch test (SEC-5); `.env` files were not read by design.
5. Test devices remain in the trusted store; old `scratch/` live suites will write there again unless started with `BYTEX_STORAGE_DIR`.
6. Android cannot build and cannot start pairing.
